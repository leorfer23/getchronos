JOBS — agent work the operator does not sit in front of: "every weekday at 9 check the exports", "in 20 minutes run the probe", "every hour triage the channel". A job = instructions (goal), a backend + model, a working directory, the tools it may use, and a schedule. Every run is recorded — status, cost, a summary and a plain-English story — and he reads them on the Desk (`⋯ → Jobs`). The run-time engine (sandbox, timeouts, retries, rate-limit resume, verifier, per-repo gates) is the same one every ticket build uses.
- CREATE: `~/.mc/bin/mc job new --name "<plain name>" --goal "<the instructions>" --workspace <id> [--cron "0 9 * * 1-5" | --at "2026-09-12 09:00"] [--cwd <dir>] [--backend claude-code] [--model sonnet|opus|haiku] [--allowed-tools "Read,Grep,Glob,Bash"]` — or POST /api/jobs {name, goal, workspace_id, cwd, backend, model, trigger_type:"cron"|"once"|"manual", cron_expr?, run_at?, timezone, allowed_tools?, disallowed_tools?, sandbox?, timeout_sec?, max_budget_usd?, notify?}. Times the operator says are in HIS timezone: send `timezone` with a cron, and an ISO time WITH offset for `run_at` (`mc job new --at` does this for you).
- PRESETS: hourly `0 * * * *` · every 30 min `*/30 * * * *` · daily 09:00 `0 9 * * *` · weekdays 09:00 `0 9 * * 1-5` · weekly Monday 09:00 `0 9 * * 1`. A one-timer is trigger "once" + run_at; after it fires it stays as a manual job with that run in its history.
- LIMIT WHAT IT CAN TOUCH: a job that only reads and reports gets `allowed_tools` "Read,Grep,Glob,WebFetch" (no Edit/Write/Bash); anything that edits a repo runs in its own worktree and gets `sandbox` "guard". `timeout_sec` and `max_budget_usd` cap a runaway.
- DRIVE: run now POST /api/jobs/:id/run · pause/resume PATCH /api/jobs/:id {enabled:false|true} · edit PATCH {goal|cron_expr|model|cwd|sandbox|allowed_tools|…} (or `mc job update <id|name> --cwd … --model …`); a cwd outside the workspace's repos/worktrees/landing dir, or a sandbox below its floor, is a 400 with the reason · history GET /api/runs?job_id=<id> · one run in plain English GET /api/runs/:id/story · kill a running one POST /api/runs/:id/kill · step INTO a run as a live terminal POST /api/runs/:id/continue {seed} (confirm first — it stops the headless process). Put a job on his screen: `UI {"op":"jobs","id":"<job id>"}`.
- MANY AT ONCE: POST /api/jobs/bulk {ids:[…], action:"enable"|"disable"|"run"|"delete"} (one schedule reload). HEALTH: GET /api/jobs/board?days=7 → every job with `recent` (last 30 runs) + `stats` (success/failed/live/cost/avg_sec/streak_failed); GET /api/jobs/runs?status=failed&days=1 → what failed across jobs. To SHOW him the page: UI {"op":"jobs"} (or {"op":"jobs","id":…} for one job).
- A recurring job costs money forever: before creating one, confirm schedule + model in ONE line unless he already said exactly that. A one-timer or a manual job: create it and report name + when. `notify` ("all"|"failures"|"off") is what run endings reach him on Telegram; default all.
- Name jobs the way he talks about them ("morning airflow check", "hourly slack triage"); never with a machine prefix (`ticket:`/`review:`/… are the fleet's own runs, not jobs he set up).
